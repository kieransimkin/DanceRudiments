# Versioned release demos and Pages

The **Release demo** workflow builds the exact tagged native catalogue, its
standalone visualizers, and a separate [3D mesh dance gallery](mesh-demos.md).
It packages the root visualizer and `meshes/` together, attaches verified
downloads to the same GitHub Release, and can deploy that complete site to
GitHub Pages. Building, attaching, deploying and checking the live site are
separate gates.

## What changes on the website

The root remains the existing native pattern visualizer. A link in its header
opens `meshes/`, where two original low-poly skinned characters perform different
recorded dances. The standalone HTML download remains self-contained; the mesh
gallery is a separate HTTP-served bundle with locally bundled JavaScript, WASM,
rig profiles and selectively loaded motion files.

Earlier skeletal-motion changes added APIs, Rigify profiles, import tools and
optional packages. Those changes did not turn the XYZ pattern visualizer into a
mesh renderer. Before this release policy, a successful **Pattern visualizer**
main-branch deployment could republish the existing 2D viewer with no visible
3D page. That result does not show that the skeletal API patch failed.

With this change, **Pattern visualizer** builds and tests main/PR previews as
artifacts only. **Release demo** is the sole Pages publisher. It deploys the
combined `dist/pages` tree, so a later main-branch preview cannot remove the
mesh gallery.

## Trigger and source identity

The workflow runs on pushes of `vMAJOR.MINOR.PATCH` tags. It also accepts a manual
`release_tag` for an existing published release whose tagged source contains
these tools. It does not use a `release.published` event generated by another
workflow's `GITHUB_TOKEN`.

For a tag push, the checked-out commit must equal both the peeled tag and the
triggering push commit. A manual run checks that the requested release exists
and is published. Both paths validate the native, Python and npm versions with
`tools/release_version.py verify-tag`. Before attaching assets, the workflow
checks the remote tag again, including annotated tags, against the tested
commit.

Publish a **fresh release containing this change** through the existing release
process. Tags predating the gallery, including `v0.3.0`, do not contain its
builders or workflow. Manually rerunning one of those tags cannot add the new
code, and existing tags must remain unchanged.

GitHub's [workflow-trigger documentation](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow)
explains why ordinary events created using `GITHUB_TOKEN` do not start another
workflow. The tag-triggered build works alongside the existing tag-release
workflow and waits for that workflow's GitHub Release before attaching assets.

## Build and browser gates

The tagged job verifies all generated default collections, installs that
checkout's native Python extension, and calls the native `catalogue()` and
`sample()` APIs. It enumerates the actual catalogue rather than maintaining a
second list of movements. Required default names are checked against
`collections/defaults.json`, so a stale installed binary cannot silently
generate a smaller viewer.

The general catalogue builder embeds native samples, source notices, interface
code, CSS and a freshly compiled C++ WebAssembly snapshot sampler into one
offline HTML file. The renderer checks every pattern's native sample digest,
negative and extreme pip wrapping, desktop/mobile rendering, filters and
playback. The MIDI harness runs against the same full viewer. Club and
Dancefloor audition pages keep their separate existing browser gates.

The mesh stage then builds only the two pinned dance sources selected in
`tools/mesh_demo_sources.json`. This is an explicit workflow download, bounded
to those two hashed files. It uses the optional package loader and the existing
native recording WASM sampler. Browser QA checks:

- Both weighted triangle skins and their changing deformed vertices.
- Every normalized and physical channel at four reference pips per dance, plus
  all source-space joint matrices against independently composed references.
- Play, pause, integer-pip seeking, preview speed, restart and complete-action
  endpoint behavior.
- No initial rig/motion/WASM download, selected-package-only loading, and native
  handle, geometry and cache disposal on switch and unload.
- Desktop and mobile layout, local-only runtime requests and browser errors.

`tools/package_release_pages.py prepare` adds only the root navigation link;
it preserves the original standalone HTML and its script/data bytes. The
complete-site browser report binds the resulting root and mesh files to their
SHA-256 hashes. `seal` accepts only the exact report schema, matching version
and commit, `scope: complete-site`, and successful coverage of both `boxbot`
and `prism`. Changed, missing, unchecked or symlinked assets fail sealing. A
local `--gallery-only` receipt cannot seal a release site.

## Release downloads and reruns

The workflow retains the existing native viewer downloads and adds distinct
site/mesh assets:

| Asset | Contents |
| --- | --- |
| `DanceRudiments-demo-vX.Y.Z.html` and associated JSON, ZIP, PNG and checksum files | The tested standalone native catalogue viewer. |
| `DanceRudiments-visualizer.html`, `.json`, `.sha256` | Stable download names within that version's release. |
| `DanceRudiments-pages-vX.Y.Z.zip` | The complete root visualizer plus `meshes/`, notices and site manifest. |
| `DanceRudiments-pages-vX.Y.Z.json` and `.sha256` | Release identity, every site asset's size/hash, and download checksums. |
| `DanceRudiments-mesh-demos-vX.Y.Z.zip` | The mesh route under `meshes/`, including both optional motion packages and source notices. |
| `DanceRudiments-mesh-demos-vX.Y.Z-browser.json`, desktop/mobile PNGs and `.sha256` | Browser evidence for both skins, bound to the packaged bytes. |

Only the attachment job receives `contents: write`. It downloads every existing
same-name asset and compares its bytes **before uploading anything missing**.
Identical assets are retained; a different existing asset stops the run. New
attachments are downloaded again and compared. No existing release assets are
deleted or overwritten. A changed renderer/toolchain may produce different
bytes on a later rebuild; that does not authorize replacing an immutable
release attachment.

Pages ZIPs are written beside the site, never inside it. This avoids recursively
including a previous download in the next site artifact. The archives use
deterministic paths, timestamps and permissions.

## Pages deployment and verification

Deployment uses the existing repository variable
`DANCERUDIMENTS_PAGES_ENABLED == 'true'`, the `github-pages` environment and its
approval rules. An already configured Pages site continues to use those
settings. The workflow reads existing Pages configuration with
`enablement: false`; it does not enable Pages or change protections, credentials
or environment settings.

Only the latest stable official GitHub Release may deploy the production site.
The job checks this before entering deployment, then checks again after waiting
for the shared `dancerudiments-pages` concurrency slot. Older releases may still
build and attach their own downloads; the workflow records a visible Pages
skip when their tag is no longer latest. This prevents a delayed historical
rebuild from replacing the newer site.

The deploy job alone has `pages: write` and `id-token: write`. It deploys the
already tested Pages artifact. Afterward, the verifier requests both directory
routes (`/` and `/meshes/`) and every public file, comparing the returned bytes
with the exact version/commit manifest. It also verifies the hosted manifest
itself. Precompressed `.json.gz` files must have identity content encoding;
HTTP decompression must not silently change the bytes the browser loader
hashes. `.nojekyll` is deployment metadata and need not have a public URL.

The `deployed-pages-verification` artifact records this separate live check. A
successful source test, browser run, upload or deployment action alone is not
reported as a verified live site. See GitHub's
[custom Pages workflow guide](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages)
for the existing environment and artifact requirements.


### Recovering a deployment rejected by environment rules

GitHub evaluates the workflow's branch or tag against the `github-pages`
environment's allowed deployment rules. An allowed **Branch** rule for `main`
does not allow a run triggered by a `vMAJOR.MINOR.PATCH` tag. A rejected job may
have no runner or step logs; inspect its check annotations for the exact reason.

If the annotation says the release tag is not allowed, a maintainer must
explicitly authorize the tag in **Settings → Environments → github-pages →
Deployment branches and tags**. Retain the existing branch rules and other
protections. Add a rule with ref type **Tag** for the exact release, or
`v*.*.*` if the maintainer approves the ongoing versioned-release policy.
The workflow never changes these rules or bypasses their approvals.

When `render`, `attach`, and `pages-target` already succeeded, use **Re-run
failed jobs** on that same workflow run after the rule is authorized. With the
GitHub CLI, substitute the affected numeric run ID below:

```sh
gh run rerun RUN_ID --failed --repo kieransimkin/DanceRudiments
```

This preserves the original tested site and release attachments while retrying
deployment. Confirm the original `github-pages` artifact is still available
before retrying; its default retention is one day. The latest-stable-release
check and live route/file checks still apply. A full rebuild can produce changed
browser reports or toolchain output and must not overwrite immutable release
attachments. If the original site artifact has expired, prepare a fresh release
through the normal build and verification process.

The [GitHub environment guide](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments)
documents separate branch/tag rules. The [GitHub CLI manual](https://cli.github.com/manual/gh_run_rerun)
documents the failed-job retry command.

## Local build

Use a checkout with matching package versions and the native build tools,
including `clang++` and `wasm-ld` for the standalone catalogue snapshot. Follow
the temporary-directory preflight in [AGENTS.md](../AGENTS.md) before expensive
builds. The workflow pins Playwright to the version shown below.

```sh
python -m pip install '.[motion-import]' playwright==1.64.0
python -m playwright install chromium
npm ci

DEMO_VERSION=$(node -p 'require("./package.json").version')
DEMO_COMMIT=$(git rev-parse HEAD)
python tools/release_demo.py --version "$DEMO_VERSION" --commit "$DEMO_COMMIT" --output-dir dist/demo
python tools/test_midi_harness.py "dist/demo/DanceRudiments-demo-v$DEMO_VERSION.html"
python tools/render_release_demo.py "dist/demo/DanceRudiments-demo-v$DEMO_VERSION.html"

python tools/build_mesh_demo_assets.py --output-dir generated/mesh-demo-assets --cache-root .cache/motion-sources/cmu-dance --download
node tools/build_mesh_demo.mjs --assets-dir generated/mesh-demo-assets --output-dir dist/pages/meshes --version "$DEMO_VERSION" --commit "$DEMO_COMMIT"
python tools/package_release_pages.py prepare --pages-dir dist/pages --visualizer "dist/demo/DanceRudiments-demo-v$DEMO_VERSION.html" --version "$DEMO_VERSION" --commit "$DEMO_COMMIT"
python tools/test_mesh_demo_browser.py --site-dir dist/pages --output-dir dist/demo --prefix "DanceRudiments-mesh-demos-v$DEMO_VERSION"
python tools/package_release_pages.py seal --pages-dir dist/pages --output-dir dist/demo --qa-report "dist/demo/DanceRudiments-mesh-demos-v$DEMO_VERSION-browser.json" --version "$DEMO_VERSION" --commit "$DEMO_COMMIT"
```

The asset builder requires a fresh output directory and uses only verified
cached sources when `--download` is omitted. Mesh-only development and the
`--chromium` override are documented in [mesh-demos.md](mesh-demos.md).

The standalone visualizer's default renderer checks `file://` navigation. Its
explicit `--in-memory` option records that narrower mode for environments that
forbid file navigation. The mesh gallery uses HTTP because its ES modules and
optional package loader fetch separate files.

## Catalogue presentation and snapshot storage

The full catalogue remains available through collection, family, search and
review filters. Only visible cards animate; offscreen canvas backing stores are
released and restored while their phase comes from the shared clock. Personal
notes, comparison, local audio/BPM synchronization, oblique 3D paths and a
separate Z curve remain available. This generated viewer is a read-only native
snapshot; authoring export controls stay hidden.

Schema 2 stores movement tables once inside WASM, with a SHA-256 digest of the
native-exported little-endian float64 XYZ values per pattern. Signed zero is
normalized for those digests. The renderer reads samples in bounded batches and
also accepts legacy schema-1 snapshots containing decimal tables. Base64 is
decoded in bounded chunks. The general snapshot permits up to 4,096 patterns
and 4,194,304 samples; untrusted authoring packs retain their separate existing
limits. The 68-study Dancefloor page retains all 16 beat mappings, four-slot
comparison, synthesized audio and its exact scalar checks.
